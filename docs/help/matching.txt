Human vs exact matching:
  bbt default behavior is "human match", that is ignoring differences
  in casing, ignoring consecutive spaces, and ignoring blank lines.
  The opposite behavior, to make strict compare, is set with:
  -em  | --exact_match
  exact_match may be altered if **followed** by one or more of:
  -iw  | --ignore_whitespaces (default)
  -ic  | --ignore_casing      (default)
  -ibl | --ignore_blank_lines (default)
  For example, "-em -iw" will take into account blank lines and
  casing but ignore whitespaces
  Note that -iw, -ic, and -ibl are useless if not preceded by -em, 
  because they are the default setting.
  There is also a
  -hm  | --human_match
  option, equivalent to defaults "-iw -ic -ibl", if you want to
  assert on the command line that this is the required behavior.

Ignoring volatile parts:
  The comparison steps also accept an (ignoring ...) clause, that masks
  the volatile parts on both sides before comparing, keeping the
  stable part precisely checked:
    - Then I get `Build finished in 3.2 s` (ignoring time)
  Three patterns are available:
  - time : masks the common clock, date and date-time values
    (12:34, 12:34:56, 2026-10-13, 2026-10-13T12:34:56 ...)
  - dir  : masks the directory part of a path, the file or directory
    name staying checked
  - version : masks version numbers (1.0, 0.5.1, 1.2.3-dev,
    2.0.0-rc.1+meta ...)
  Several patterns combine, separated by commas or "and":
  (ignoring time, dir), (ignoring time and dir)
  A pattern that matches nothing on the actual side raises a warning,
  as the neutralization may silently weaken the test.
  cf. docs/features/A300_Ignoring.md
