# Development workflow

This document describes the workflow for normal development tasks.

Its purpose is to keep changes easy to review and ensure that commits contain
a complete, consistent and validated project state.

## 1. Development loop

Work on the source files without staging, committing or pushing.

The normal development loop is:

```sh
cd tests && make features
```

To run a single test:

```sh
cd tests && ./bbt <test_file>
```

Run another suite only when the change concerns it:

```sh
cd tests && make examples
cd tests && make non_reg
cd tests && make unit_testing
```

Useful direct test commands are:

```sh
cd tests && ./bbt ../docs/examples
cd tests && ./bbt ../docs/features
```

When running tests:

- add `--exclude Windows_Only` on Linux and macOS;
- add `--exclude Unix_Only` on Windows.

Run the relevant tests throughout development. Fix failures before continuing.

## 2. Feature and error-message changes

Feature files in `docs/features` are the specification. Follow a TDD-first
approach when changing a feature or an error-message format.

Avoid snapshot testing, especially for generated files. Refer to
`docs/bbt-skill` for the project testing approach.

For every functional change:

1. update the relevant feature files;
2. implement the change;
3. update or add the relevant tests;
4. update the documentation, examples and help text where applicable;
5. add a changelog entry under the current `-dev` version.

Changelog entries must:

- be short;
- announce the user-visible change in one line;
- reference the relevant feature file or issue for details;
- be added at the top of the appropriate list so that the latest entry comes
  first.

The changelog is for users. Do not record changes to the bbt skill itself.

Do not hard-code the current bbt version in examples or generated
documentation. Use a regular expression or a fixed behaviour instead.

When checking tool messages, set the environment consistently:

```gherkin
Given the environment variable LC_ALL is set to C
```

This prevents generated examples and documentation from depending on the
machine or locale.

## 3. Embedded help and generated documentation

Files in `docs/help/` are embedded in bbt at build time through
`External_Initialization`.

After changing embedded help:

1. rebuild bbt before testing the help;
2. regenerate the relevant reference files, including
   `docs/examples/gcc_hello_world.md`;
3. ensure that test B130 passes.

The embedding is performed by the binder. If `make build` reports that
everything is up to date but the embedded help is stale, remove:

```text
obj/<profile>/b__bbt-main.*
```

Then rebuild to force the rebind.

For any functional evolution, review whether the following files also need to
be updated:

```text
docs/help/tutorial.md
docs/help/example.md
docs/examples/gcc_hello_world.md
```

Fixme comments in `docs/` and `src/` are indexed in:

```text
docs/dev/fixme_index.md
```

The index is regenerated by:

```sh
make doc
```

Remove Fixme comments made obsolete by the change and propose closing the
related issue when appropriate.

When writing Markdown:

- align tables with spaces so that they remain readable as plain text;
- generated files such as `docs/grammar.md` and `docs/keywords.md` are exempt;
- to display a whole step between backticks while preserving inner backticks,
  use a double-backtick code span with a space before the closing delimiter.

## 4. Review implementation completeness

When the relevant tests pass, verify that all impacted project elements are up
to date, including where applicable:

- source files;
- feature files;
- tests;
- documentation;
- embedded help;
- examples;
- changelog;
- Fixme comments and index;
- project and build files;
- generated documentation and indexes.

Review the modified sources critically:

- is the implementation complete?
- is obsolete code left behind?
- should anything be moved or factorised?
- is there duplication that should be removed?
- are comments and documentation still accurate?
- are there unrelated changes?

Do not stage the changes yet. Modified, staged and untracked files must remain
available for review in the editor and through Git tools.

## 5. Clean before owner review

When the development loop is green, run:

```sh
make clean
```

Then inspect the working tree:

```sh
git status
git diff
git diff --staged
```

Review all:

- modified files;
- staged files, if any already existed;
- untracked files.

The repository may contain useful uncommitted changes, but it must not contain
unwanted:

- test artefacts;
- generated temporary outputs;
- debug traces;
- editor files;
- compiler outputs;
- unrelated files.

Check the file system directly, not only `git status`. Git-ignored artefacts
such as `input._`, `expected__` or `cp...` remain invisible to Git.

Files created by `When I run` steps, such as binaries compiled by `gcc`, are
not tracked by the bbt `--cleanup` option. That option only tracks files
created by `Given` steps.

If `make clean` leaves an unwanted artefact behind, update the clean target so
that this type of artefact is removed automatically in the future.

After changing the cleanup rules, run `make clean` again and repeat the
file-system and Git review.

## 6. Owner review and approval

The owner reviews the useful modified, staged and untracked files before any
new staging, commit or push.

Present a concise report containing:

- what was changed;
- which tests were run;
- the result of those tests;
- the documentation and changelog updates;
- any generated files that changed;
- the files currently modified, staged or untracked;
- any remaining warning, uncertainty or proposed follow-up.

Then ask explicitly for approval to perform the final validation, commit and
push.

Do not run `git add`, `git commit` or `git push` before receiving this
approval.

## 7. Final validation after approval

After the owner gives approval, run the complete validation:

```sh
make all
```

This covers the complete build, SUT, checks and documentation generation.

If any step fails:

1. stop;
2. do not stage, commit or push;
3. report the failure;
4. ask the owner to arbitrate if necessary.

If `make all` succeeds, run:

```sh
make distclean
```

Then inspect the working tree and the file system again:

```sh
git status
git diff
git diff --staged
```

Verify that:

- no unwanted test or build artefact remains;
- no Git-ignored artefact remains on the file system;
- all intended generated results, badges and indexes are present;
- cleanup has not removed a file that must be committed;
- the remaining changes are exactly those intended for the commit.

If an unwanted artefact remains, update the cleanup rules and repeat the
necessary validation.

## 8. Stage and review the complete generated state

Once the final validation and cleanup are successful, stage the complete
approved state:

```sh
git add <approved files>
```

The staged state must include all intended generated results, badges, indexes
and documentation produced by the full run.

Do not commit in the middle of the generation chain. For example, committing
after the feature tests alone can freeze inconsistent artefacts, such as:

- a `badge.url` file still containing the bbt placeholder;
- a stale `badge.svg`;
- stale test results, indexes or generated documentation.

Review the exact staged content:

```sh
git status
git diff --staged
```

If the staged state differs from what the owner approved, stop and report the
difference before committing.

## 9. Commit, rebase and push

Create a focused commit describing the approved change:

```sh
git commit
```

Before pushing, synchronise with the remote main branch:

```sh
git pull --rebase origin main
```

The CI may have pushed commits updating test results and badges since the
previous local synchronisation. A plain push may therefore be rejected.

If the rebase conflicts:

- for generated test results, badges and similar generated files, keep the
  local version produced by the latest complete local run;
- for source files, documentation or any non-generated file, stop and ask the
  owner to arbitrate rather than resolving the conflict silently.

After a successful rebase, push:

```sh
git push
```

Do not amend commits, force-push or rewrite published history without explicit
owner approval.

Report:

- the commit created;
- the branch pushed;
- the rebase result;
- the push result;
- any CI checks triggered by the push.

## 10. Design discussions and proposed features

Record design subjects in:

```text
docs/dev/design_discussions.md
```

Use one entry per subject, with one of these statuses:

- under discussion;
- arbitrated.

An arbitrated entry must state:

- the decision;
- the rejected alternatives;
- why they were rejected;
- the pull request or discussion where the subject was elaborated.

The document header contains a table of entries sorted by status, with subjects
under discussion first.

A reference from the source code to a design-discussion entry is welcome when
it helps understanding.

The developer guide contains operational descriptions only. Move discussions
of alternatives and design decisions to `docs/dev/design_discussions.md`.

Record an undecided feature idea in:

```text
docs/proposed_features
```

Also add an entry to the TDL chapter of:

```text
docs/dev/project.md
```

The proposal may be a short description of the need or a complete feature file
with scenarios, ready to move to `docs/features` once the decision is made.
See `docs/proposed_features/pty.md` as an example.
